# OpenXR virtual reality

> Archived 18 October 2026. Historical plan and evidence; the [development roadmap](../../../roadmap.md) is the single active plan. Old priorities, checkboxes and support claims are not current status. Technical requirements incorporated by the roadmap remain traceable here.

Status: phases 1–3 implemented 2026-10-02 and passing against the OpenXR test
runtime on Windows (`tools/tests/openxr_vr_smoke.py`); the Linux sources and
loader compile under GCC. A run on real headset hardware is still open, and
phase 4 onward is follow-up work. Phase 4 has the aim marker, haptics, room
scale (single player and multiplayer), physical crouch, held and two-handed
weapons, the comfort vignette, scope zoom and single player vehicles in
stereo so far (2026-10-04).

Design guidance for phase 4 comes from Team Beef's
[PreyVR](https://github.com/Team-Beef-Studios/PreyVR) (Luboš Vonásek,
GLKarin, DrBeef, Baggyg, Bummser and contributors, GPL-3.0), an idTech 4 VR
port that takes its renderer and VR integration from DrBeef's
[Doom3Quest](https://github.com/DrBeef/Doom3Quest) (GPL-3.0): their feature
lists and approaches (head-driven movement, laser sight, weapon wheel,
two-handed aim, height adjustment, full-motion crouch) are the reference for
what an idTech 4 game needs in VR. openQ4 reimplements ideas; no PreyVR or
Doom3Quest code is copied. Both projects are credited in the README.

openQ4 gains a native PC VR mode built on OpenXR. A player with any
OpenXR-conformant PC runtime (SteamVR, Meta Quest Link/Air Link, Virtual
Desktop's VDXR, Pimax, Varjo, Monado on Linux) sets `vr_enable 1` and plays
the single-player campaign or multiplayer with stereo rendering, head tracking,
motion-controller aiming and a floating virtual screen for menus, the HUD,
loading screens and cinematics.

## Goals

- Stereo first-person rendering at the headset's resolution and refresh rate,
  with each eye's exact off-axis projection and late-latched head pose.
- Six-degree-of-freedom head tracking layered over the player's body, without
  touching collision or multiplayer prediction.
- Motion-controller input through the existing binding system, so default
  gamepad binds, menu navigation and rebinding keep working.
- Controller aiming that stays multiplayer-safe: aim is carried by the existing
  usercmd angles, so servers need no protocol change.
- Everything flat (menus, HUD, console, loading screens, cinematics) on a
  composited quad layer instead of being painted into the eyes.
- Comfort defaults: snap turn, no camera bob/kick/roll, no forced camera
  rotation; the in-engine cinematics play on the virtual screen.
- Zero cost when VR is off: no OpenXR call is made, and the dedicated server
  never links OpenXR.
- Stock-asset compatibility: no new content is needed to play in VR.

## Non-goals for the first deliverable

- Vulkan presentation. `XR_KHR_vulkan_enable2` makes the runtime create the
  instance and device, which conflicts with the renderer's device selection
  (`docs/dev/vulkan-device-selection.md`). VR requires `r_renderApi gl` for now
  and says so when Vulkan is active.
- Standalone Android headsets (Quest native). The GLES module and
  `XR_KHR_android_create_instance` are a separate track.
- Room-scale locomotion in multiplayer. There the server owns positions, so
  physical movement only offsets the camera within limits; single player
  walks the body after the head (added 2026-10-03, see Game).
- Hand-presence models, two-handed weapons, physical interaction with world
  objects, and per-weapon hand-alignment tuning beyond one offset set.
- Temporal anti-aliasing and dynamic resolution in VR. Both keep one history
  per frame; they are forced off while presenting to a headset.

## Constraints from the code

These come from a survey of the frame loop, renderer modules, GL backend, game
view and input code (recorded here so later work does not re-derive them).

- **One thread, synchronous backend.** `idCommonLocal::Frame` paces in
  `openQ4_BeginPresentationFrame`, runs game tics, then `UpdateScreen` runs
  `BeginFrame` → `Draw` → `EndFrame`, and `EndFrame` executes every render
  command and swaps (`RenderSystem.cpp` `R_IssueRenderCommands`). There is no
  render thread, so an OpenXR frame can bracket one `UpdateScreen`.
- **The renderer is a module that owns the GL context.** The exe owns the SDL
  window and input; `renderer-gl_<arch>` creates and owns the context through
  window services. Native GL handles (HGLRC, GLXContext) are only reachable
  inside the module, so the module reports them for the XR graphics binding.
- **One `idRenderSystem` implementation** (`idRenderSystemLocal`) serves the
  GL, Vulkan and GLES modules; its vtable is ABI with append-only slots
  (`RENDER_API_VERSION`), and game modules call it too (`GAME_API_VERSION`).
- **"No render target" means the window.** About twenty backend sites bind
  framebuffer 0 and `GL_BACK`, the colour-mapping/CRT swap tail copies the
  window, and `glConfig.vidWidth/vidHeight` size the crop stack, the 2D
  viewport, the temporal presentation extent and every game render target.
- **The game owns the scene pipeline.** `idGameLocal::RenderScene`
  (`src/game/Game_render.cpp`) renders into game render textures, resolves
  MSAA, runs SMAA/blur and composites into "the back buffer"; multiplayer calls
  `RenderScene` directly. `idPlayerView::RenderPlayerView` already splits the
  3D pass (`RF_NO_GUI | RF_PRIMARY_VIEW`) from the 2D pass (`RF_GUI_ONLY`).
- **Off-axis projection exists** for levelshot tiles
  (`tr_levelshotProjectionShift*` in `tr_main.cpp`): projection, frustum
  planes and shadow cascades already accept arbitrary near-plane extents.
- **Aim is the usercmd.** `usercmd_t::angles` are absolute; the game maps them
  through `deltaViewAngles`, and in multiplayer the server simulates with them.
  Movement follows the aim yaw.
- **Bindings run through the key queues.** A controller button must reach both
  the `SE_KEY` event queue and the keyboard poll queue
  (`SDL3_PostControllerKeyEvent`) or usercmd binds such as `_attack` never fire.
  Menus hard-code the gamepad JOY codes for navigation.

## Architecture

```
            exe (client only)                     renderer-gl module
  ┌────────────────────────────────────┐     ┌───────────────────────────────┐
  │ idVRSystemOpenXR (src/sys/openxr)  │     │ idRenderSystemLocal           │
  │  instance/session/spaces/actions   │────▶│  GetVRGraphicsBinding (HGLRC, │
  │  swapchains, xrWait/Begin/EndFrame │     │    GLX handles)               │
  │  poses → vrFrameState_t            │◀────│  SetVRFrame (swapchain GL     │
  │  controller → keys, move, turn     │     │    names, sizes)              │
  └───────────────┬────────────────────┘     │  SetVRRenderTarget(eye / UI)  │
                  │ idVRSystem (gameImport)  │  backend: redirected default  │
                  ▼                          │    framebuffer, blits, mirror │
  ┌────────────────────────────────────┐     └───────────────────────────────┘
  │ game-sp / game-mp                  │                  ▲
  │  per-eye renderView (off-axis FOV) │──────────────────┘
  │  view weapon at the hand           │
  └────────────────────────────────────┘
```

### Build

- `subprojects/openxr.wrap` pins the Khronos OpenXR SDK 1.1.63 source tarball;
  `subprojects/packagefiles/openxr/meson.build` builds only the loader, as a
  static library, against the project's existing jsoncpp subproject. No
  `openxr_loader` DLL ships; runtime discovery (`XR_RUNTIME_JSON`, the Windows
  `ActiveRuntime` registry value, XDG `active_runtime.json`) is the upstream
  loader's.
- `meson_options.txt` gains `openxr` (feature, `auto`). It is effective only for
  the SDL3 client on Windows and Linux; macOS, Android and every dedicated
  server build without it.
- Client-only sources live in `src/sys/openxr/` (not covered by the engine
  globs) and are appended after the dedicated-server source snapshot. The
  client compiles with `OPENQ4_OPENXR=1`.
- `src/framework/VRSystem.cpp` (globbed into every engine target) provides the
  interface, the cvars and the null implementation used when OpenXR is absent.
- The OpenXR SDK's Apache-2.0 notice joins `docs/licenses/` and the release
  notice list.

### Coordinates and units

`src/framework/VRMathCore.h` (dependency-free, unit-tested) owns every
convention: OpenXR (+X right, +Y up, −Z forward, metres) to engine (+X forward,
+Y left, +Z up, game units) is a proper rotation, so directions permute,
quaternions permute their vector part and positions scale by `vr_worldScale`
(default 39.37 units per metre: Quake 4's 68-unit eye height is 1.73 m).
Engine yaw is counter-clockwise from above; a positive pitch looks down.

### Frame timeline (one `UpdateScreen`)

1. `vrSystem->BeginFrame()`: poll events; `xrWaitFrame` (this is the frame
   pacer while a session runs: `com_maxfps` and window vsync are bypassed);
   `xrBeginFrame`; `xrSyncActions`; locate head, eyes (`xrLocateViews` at the
   predicted display time) and both controllers; acquire and wait one image of
   each swapchain; hand the GL texture names and sizes to the renderer with
   `SetVRFrame`.
2. `renderSystem->BeginFrame()`: while VR presents, the frame's output is the
   virtual-screen target, not the window; temporal AA, dynamic resolution and
   the legacy fill-rate crop are bypassed. The virtual screen is 1920 texels
   wide and takes the window's 2D-viewport aspect (clamped to 4:3–32:9):
   stock GUIs, retained documents and the HUD all lay out for the window
   (`engineWindowState.uiViewport*`) and their 640×480 canvas stretches over
   whatever target they draw into, so any other shape would distort them. A
   window resize recreates the screen swapchain between frames.
3. Game draw. In first-person gameplay the player view renders the 3D pass once
   per eye between `SetVRRenderTarget(eye)` and `SetVRRenderTarget(-1)`; each
   eye's `renderView_t` carries the off-axis tangents. Everything else — HUD,
   menus, console, loading screens, cinematics — draws to the virtual screen.
4. `renderSystem->EndFrame()`: the backend finishes each target (gamma/colour
   mapping), blits eyes and the virtual screen into the acquired swapchain
   images, draws the desktop mirror and swaps the window without vsync.
5. `vrSystem->EndFrame()`: release images; `xrEndFrame` with a projection
   layer (only when both eyes were rendered this frame, using the exact poses
   and FOVs the eyes were rendered with) and a quad layer for the virtual
   screen (head-locked HUD placement during gameplay, a larger world-locked
   screen otherwise).

Presents that happen outside `UpdateScreen` (startup splash, vid_restart) do
not open an XR frame and draw to the window as before.

### Renderer

- `renderView_t` gains `asymmetricFov` and four half-angle tangents with
  default member initializers, so every existing producer, demo and save stays
  symmetric. `R_SetupProjection`, `R_SetupViewFrustum` and the cascaded
  shadow-map extents read near-plane extents from one helper that honours
  either the levelshot shift or the view's tangents. `fov_x/fov_y` still carry
  the enclosing field of view for estimates (LOD, light grid, effects).
- New append-only `idRenderSystem` slots (render API 21, game API 50):
  `GetVRGraphicsBinding`, `SetVRFrame`, `SetVRRenderTarget`,
  `GetVRFrameResult`. The Vulkan and GLES modules report no binding.
- **Redirected default framebuffer.** The GL backend gains a "default target":
  framebuffer 0 for desktop frames, or an eye/virtual-screen render texture
  while VR presents. Every site that bound framebuffer 0 for "the back buffer"
  goes through one helper; `glDrawBuffer(GL_BACK)` becomes
  `GL_COLOR_ATTACHMENT0` on a redirected target. A `RC_VR_TARGET` command
  switches the target and the backend-visible output size in command order;
  the front end switches its crop, 2D viewport and presentation extent at the
  same point, so the game's targets are sized for the eye.
- The renderer owns its eye and virtual-screen render textures (RGBA8 + depth/
  stencil at eye size). Swapchain images are only ever blit destinations, so
  the runtime's formats never constrain the pipeline. The engine requests
  `GL_SRGB8_ALPHA8` swapchains and the blit writes the gamma-encoded pixels
  unchanged (framebuffer sRGB stays off), which is what the compositor expects.
- Mirrors and other per-frame subview captures are re-rendered per eye. The
  view weapon keeps its depth hack (depth only, so the stereo pair is intact,
  and a hand pushed into a wall still shows its gun); only the `cl_gunfov`
  projection override is skipped for off-axis eyes, since a symmetric gun
  FOV would tear the pair.

### Game (src/game and src/mpgame)

- Eye views are built at draw time from the latest head pose: the world origin
  is the player's interpolated eye position (bob, kick and shake removed), plus
  the tracked eye offset rotated by the body yaw; the axis is the body yaw
  composed with the tracked eye orientation. Body yaw is the VR turn
  accumulator plus `deltaViewAngles.yaw`, so spawns, teleports and movers keep
  working.
- **Room scale** (`vr_roomScale`, added 2026-10-03 for single player and
  2026-10-04 for multiplayer, after
  PreyVR's head-driven movement). Once the tracked head is more than 4 units
  from the tracking origin horizontally, `idPlayer::UpdateVRRoomScale` walks
  the body the rest of the way before the tic's `Move()`:
  `idPhysics_Player::VRWalk` borrows `SlideMove` (walls, steps up and down)
  for that one displacement without touching the velocity, so no momentum
  or footsteps follow, and refuses a step off solid ground. The distance it
  actually covered goes back through `idVRSystem::ShiftTrackingOrigin`, which
  moves the recentre pose and this frame's poses by it. The camera therefore
  stays on the head with no double movement, and a blocked body leaves the
  head to the `vr_headOffsetLimit` clamp instead of a wall.

  A multiplayer server moves bodies only from usercmds, so there the engine
  walks the body the way PreyVR does, through the usercmd: while the
  locomotion stick rests, `VR_RoomScaleWalkInput` turns the head's offset
  into movement in the aim frame, up to half of full input 12 units out.
  The body then coasts after its input stops, so the walk starts only
  beyond 6 units and runs until the head is within 2, and the coast ends
  inside the free zone instead of setting off a walk back. The local player
  (`idPlayer::ReportVRRoomScaleWalk`, on the listen server's tic and in the
  client's leading prediction pass) reports each new tic's predicted
  horizontal progress through `ShiftTrackingOrigin`, and the engine keeps it
  only while it walked the body or within 400 ms of it, with the stick at
  rest: stick movement, knockback and movers stay out of the tracking space,
  and a jump of more than 32 units (a teleport or respawn) is ignored. No
  interface changed. Measured on `mp/q4dm1`, a 0.5 m step leaves the head
  2.9 units behind the body once it stops, against 4.1 units without the
  hysteresis, where the next walk would start.
- Cinematic cameras, private cameras, third person and (in multiplayer)
  spectating render flat onto the virtual screen. So do vehicles while
  `vr_vehicleStereo` is 0, and always in multiplayer, which has none; single
  player vehicles otherwise render in stereo (see Vehicles).
- The view weapon follows the weapon-hand controller in controller-aim mode
  (`vr_aimMode 1`).
- **Held weapons** (added 2026-10-03). Quake 4 draws view weapons squashed
  along their length (`foreshorten`, 0.44 to 0.66) and points their barrels
  1 to 16 degrees left and up of the model's forward axis, so that they
  converge on a crosshair at the centre of a flat screen. In a hand, both
  look wrong: a stubby gun that points away from its own laser.
  `rvWeapon::GetVRHold` therefore measures how each model holds its gun, once
  per view model and from the first frame of its idle animation (an
  `ANIM_CreateAnimFrame` evaluation, so the hold stays put while the gun
  animates): the barrel is the flash joint's forward axis, the way the muzzle
  flash leaves it, and the grip is halfway between the `rt_wrst` and
  `rt_ndx_1` joints, the right wrist and index knuckle that every stock view
  mesh carries. `VR_WeaponTransform` turns the barrel onto the hand's aim by
  the shortest rotation (`VR_RotationBetween` in the math core) and puts the
  grip point on the controller's grip pose, the palm, so the gun points where
  the laser and the shots go. `rvWeapon::ForeshortenAxis` returns the axis
  unscaled while the player aims with a hand, which keeps the render entity,
  bound effects and the muzzle on one true-scale pose. `vr_weaponOffset*` and
  `vr_weaponPitch` now default to 0 and only fine-tune the hold in the aim
  axes. A model without the joints is held straight ahead at (13, -5, -5),
  where the stock models put the right hand. PreyVR tunes a hand-picked
  offset table per weapon instead; the joints make that unnecessary for
  Quake 4's arsenal and for mod weapons built on its rigs.
- **Two-handed aim** (`vr_twoHanded`, added 2026-10-03, after PreyVR's
  off-hand grip modifier). The off-hand grip squeeze opens the weapon wheel,
  unless it closes with that palm on the gun's foregrip: up to 0.65 m ahead of
  the weapon hand's palm and within 0.2 m of its aim
  (`VR_OffHandOnForegrip`). Then the squeeze posts no key, gives the off hand
  a 20 ms buzz, and until release the weapon hand's aim keeps its origin and
  roll but points from its palm through the other one (`VR_TwoHandedAxis`,
  applied in `ApplyTwoHandedAim` before the usercmd reads the aim). Which of
  the two the squeeze does is decided when it closes, so a hand that drifts
  onto or off the gun mid-squeeze changes nothing. Because the override sits
  in the shared aim pose, the usercmd, the drawn gun, the laser and the shots
  all follow it, with no server change for multiplayer. PreyVR derives the
  same line from the two hands while its off-hand grip is held, with a
  per-weapon switch; the foregrip test lets one button keep both jobs.
- **Comfort vignette** (`vr_comfortVignette`, default 0.5, added 2026-10-03;
  PreyVR offers a reduced field of view among its motion-sickness aids).
  While the stick moves the player or turns them smoothly, each eye darkens
  towards its edges around a clear centre on its own optical axis, so the
  pair fuses at infinity. `idPlayerView::VRComfortVignette` follows only
  artificial motion: the player's velocity (a room-scale step restores it,
  so walking about the room never triggers it) and the tracking yaw's rate,
  where a change of more than 15 degrees in one frame is a snap turn or a
  recentre, a cut rather than motion. `VR_ComfortMotion` maps a run (160
  units/s) or a 120 degrees/s turn to full strength; `VR_ComfortEase` eases
  in within about 0.1 s and out over about 0.35 s. `VR_DrawComfortVignette`
  draws 24 smoothstep rings and a solid edge in each eye's 2D pass, under the
  aim marker; at strength 1 the clear centre is 60 degrees across and the
  edge is black. The game reads the engine cvar by name, so neither the frame
  state nor an API version changed.
- **Physical crouch** (`vr_physicalCrouch`, added 2026-10-04, after
  Doom3Quest's full-motion crouch). A head 0.4 m below where it was
  recentred crouches the body until it rises above 0.3 m
  (`VR_PhysicalCrouch`); the engine sets `BUTTON_VRCROUCH`, a new usercmd
  button (bit 10 of the networked short), and `idPhysics_Player` ducks on it
  as on a held crouch, so a multiplayer server crouches the body as well.
  The separate bit tells the game the crouch came from the head: the
  tracked head is already down, so `idPlayer::VRCrouchLift` raises the
  tracking origin back to the standing eye height (68 units; a Quake 4
  crouch drops the eye 36) instead of lowering the view twice, but keeps it
  within 16 units of the crouched eye, as far as `vr_headOffsetLimit` lets a
  head lean sideways, so a shallow real crouch cannot see over what hides
  the body. A button crouch (`upmove`) latches no lift until the body stands
  again, so it lowers the view as on a flat screen and releasing it does
  not jump. The eyes, hands, gun and laser use the lifted origin;
  multiplayer shots still leave the body's eye.
- **Zoom** (added 2026-10-04, after PreyVR's fluent rifle zoom). The
  headset's field of view cannot narrow, so `idPlayerView::VRView` scales
  each eye's frustum tangents by `VR_ZoomTangentScale( CalcFov( true ),
  CalcFov( false ) )`, the weapon's own zoom ratio as the flat screen eases
  it, at most 3x. In hand aim the scope picture is not drawn, because it
  sits head-locked on the HUD and would point where the head looks; the
  laser dot, projected through the same tangents, is the reticle, and the
  beam stands down to a dot so the hidden gun's line does not cross the
  magnified view. The gun hides while scoped, as on a flat screen. Head aim
  keeps the scope picture, which is centred on its aim.
- In single player, projectiles and hitscans start from the controller; in
  multiplayer they start from the eye along the controller's aim (the server
  only knows usercmd angles), which keeps prediction and lag compensation
  unchanged.
- **Aim marker** (`vr_aimLaser`, added 2026-10-03). The screen-centre
  crosshair stands down in controller aim because it would mark the head's
  aim, not the gun's. Instead `idPlayer::GetVRAimMarker` traces the shot's own
  path once per frame (from the hand in single player, from the eye in
  multiplayer, `MASK_SHOT_RENDERMODEL` like hitscans) at the presentation
  pose the view weapon is drawn at, and `VR_DrawAimMarker`
  (`VRSystem.h`) draws it into each eye between its 3D pass and its fade, at
  that eye's projection of the hit point (`VR_EyeTangentOf`,
  `VR_TangentToImage` in the math core). The pair therefore fuses at the
  target's depth, which a HUD-plane crosshair never can. The dot keeps a
  fixed angular size (0.57 degrees across) and dims when a trace from the head
  finds the target hidden, as round a corner the hand sees past. Mode 2 adds
  a beam from the drawn weapon's flash joint (`rvWeapon::GetVRMuzzle`) that
  fades out within 4 m; its quads narrow with depth. The marker is local
  drawing only: servers see nothing new. It is 2D over the eye, which is
  safe because the shot's path ends at the first surface. Triangles in the 2D
  pass are culled by winding, so every disc and beam quad is counter-clockwise
  in tangent space. The marker hides with the weapon (holstered, hidden, a
  zoom GUI that hides the crosshair) and while a world GUI has focus.
- **Haptics** (added 2026-10-03). `idVRSystem::Vibrate` (an appended slot)
  applies `xrApplyHapticFeedback` to the vibration action on one hand's
  subaction path, scaled by `vr_hapticStrength`, only while the session has
  input focus. `idPlayer::VRVibrate` gates it to the local player and to new
  frames, since a multiplayer client reruns frames for prediction.
  `rvWeapon::Attack` pulses the weapon hand for 40 ms per shot (stronger for
  a spread of pellets), and `idPlayer::ClientDamageEffects` pulses both hands
  for 90 ms, harder for bigger hits.
- **Vehicles** (`vr_vehicleStereo`, single player, added 2026-10-04). Sixteen
  campaign maps place vehicles (the GEV hovertank, the walker, the Air
  Defense big gun, tram guns, drop pods, the medical bed), and Quake 4's
  vehicle view is the turret: the camera rides the eye joint and the mouse
  turns it. In VR the turret follows the head instead
  (`idPlayer::GetVRVehicleAim`), as the mouse did: look where you shoot, and
  an enclosed cockpit stays in front of the eyes, where hand aim swung the
  walker's canopy across the view. The trigger fires, and the aim dot traces
  the vehicle's own eye axis, the line its shots converge on, so it shows
  where the turret points while it catches up. In a seat the HUD hangs on the
  line of sight, as in head aim, whatever `vr_aimMode` says: the game sets
  the read-only `vr_hudOnSight` each stereo frame and the engine drops
  `vr_hudHeightOffset` for it, so the big gun's ring sight and the vehicle
  crosshair sit on the turret's line rather than 4 degrees under it. Five
  traps shaped the result:
  - *The eye joint is off the turret's axis.* The GEV's eye sits 56 units
    ahead of its turret pivot, so a quarter turn after the head swung the
    camera some 70 units. `rvVehiclePosition::GetVRSeat` moves the eye onto
    the axis of the position's yaw turret (`rvVehicleTurret::GetYawPivot`),
    keeping its height above the pivot along the hull's up, so the vehicle's
    animation (the walker standing up after entry) still carries it and a
    pitching cockpit moves it a unit or two, as a neck does in a nod.
    Freezing that height at entry left the eye a metre inside the walker,
    caught mid-stand-up; measuring it along the eye's own up sank it too.
  - *Turrets only take input deltas, clamped to their turn rate.* A tracked
    head or hand turns further in a frame than a mouse, so the clamp dropped
    the rest: 45 degrees of hand turned the GEV turret 4.6. A turret that
    carries the position's eye in the skeleton
    (`rvVehicleTurret::CarriesJoint`) is now steered by it: each frame it
    turns, at its turn rate, from where the eye looked to where the aim
    points, both in the world, so a tilted hull and the vehicle's own turns
    cannot throw it off (open-loop deltas left the GEV, rolled 14 degrees on
    a slope, 10 to 15 degrees off the head). Any other turret keeps what the
    clamp withholds and catches up (what a stop withholds stays owed, so the
    aim leads it back out), first turning to the aim on taking the seat or
    when the aim passes between head and controller; it cannot run away
    chasing an eye it never moves. The flat game keeps its original deltas.
    Measured with the head turned 0, 45 and 90 degrees right: the walker's
    cockpit and the big gun land on 150.7, 105.7 and 60.7 (the gun stops at
    its 106.7 limit first), the GEV on 150.6, 105.7 and 60.6.
  - *Binding to the vehicle rewrites `deltaViewAngles`.*
    `idEntity::UpdateFromPhysics` turns a bound actor's view deltas with its
    master's yaw, and the driver bound to the GEV's `origin` joint lost its
    whole 150.7-degree facing on the first frame. Flat play never notices,
    as a seat never reads view angles and exiting resets them. The seat
    keeps its own facing, `vrVehicleDeltaYaw`. On taking the seat the view
    turns to where the vehicle's eye looks, as the flat view does at once;
    keeping the boarding facing instead left tram1b's rear gun behind a
    player who boarded facing forwards, pinned at the stop of its arc.
    Stepping out hands the facing back, so the world does not turn again.
  - *Whether the vehicle's turns carry the view depends on who turns it.*
    A tram on a curve or a walker turning on the spot turns its seat, so its
    yaw changes are added to the seat's facing (`UpdateVRVehicleFrame`). The
    GEV under `g_vehicleMode` steers its hull after its own turret
    (`rvVehiclePosition::TurretAlignsVehicle`), which follows the head, so
    carrying the view there would chase the aim in circles; its view stays.
    The view stays level in every vehicle: hulls pitch and roll over ground.
    On tram1b's rail ride, which seats the player on the tram's rear gun,
    the seat's facing followed the tram's yaw through every curve of 30 s of
    track at a constant offset, and the gun tracked it. Medlabs' table ride
    (the Stroggification) carries the view down its track the same way: the
    eye looks from the head along the strapped body, in stereo, through
    every stop and turn of 40 s of the ride. So do mcc_2's opening bed and
    both drop pods. storage1's pod falls for 30 s and then crashes through
    the tower, pitching between -24 and +35 degrees, its largest turn in a
    tic 2 degrees; mcc_2's launch arm swings its pod from nose down through
    level to nose up in the tube, and the level view lets the pod turn about
    the head instead of laying the player on their back. The arm stands the
    pod 0.07 degrees short of the vertical, where the nose keeps a horizontal
    sliver a thousandth long: a hundredth of a degree of sideways wobble
    would swing its yaw 8 degrees, and crossing the vertical would flip it
    half a turn. So a nose within six degrees of vertical carries nothing,
    and the seat keeps its facing until the nose has a heading again. The
    twist of each frame's rotation about the world's up has no such point,
    but it is not the nose's heading: it parted from it by up to 8.8 degrees
    over storage1's crash, where the pod rolls to -48 degrees while
    pitched, and the nose is what the seat keeps in front of the player.
  - *The engine turns the stick into the weapon hand's aim*, which a vehicle
    never sees, so a hand pointed aside made the tank strafe. The game turns
    the stick back to the head, which the vehicle faces.

  The view has no shake in a seat either; a vehicle gun's shot pulses the
  weapon hand instead (harder for guns that shake the screen), room scale
  rests while the head leans within `vr_headOffsetLimit`, and the comfort
  vignette reads the vehicle's speed and the seat's turns.
- **Weapon wheel** (fixed 2026-10-04). The wheel's cursor follows usercmd
  angle deltas, and `idPlayer::UpdateViewAngles` held the view still against
  them by rewriting `deltaViewAngles`, which in VR also turns the tracking
  space: every use of the wheel swung the world by the hand's motion and
  left it turned. In VR the angles keep following the hand while the wheel
  is open; the cursor reads its own copy of the deltas.

### Input

- `idUsercmdGenLocal` asks the VR system for the aim angles, the turn
  accumulator and the locomotion vector while a session is focused: aim from
  the dominant controller (or the head with `vr_aimMode 0`), locomotion from
  the off-hand stick relative to the head (`vr_moveDirection 0`) or the
  off-hand controller (`1`), turning by snap (`vr_turnMode 0`,
  `vr_snapTurnAngle`) or smooth (`vr_smoothTurnSpeed`). Mouse yaw still turns
  the body for seated play.
- Buttons become the JOY codes of the SDL gamepad mapping through the same
  dual path as a gamepad, so `default.cfg` gamepad binds and menu navigation
  apply unchanged: right trigger RT (`_attack`), left trigger LT (`_zoom`),
  A/B/X/Y, grips LB/RB, stick clicks L3/R3, menu Start; the weapon-hand stick's
  vertical axis pages weapons (D-pad up/down).
- On the virtual screen the weapon-hand controller is a laser pointer. Its raw
  LOCAL-space aim ray is intersected with the world-locked screen quad
  (`VR_RayQuadIntersect`), and `Sys_PostVRPointer` turns the hit into the
  window position the desktop mouse would have there: a retained `POINTER`
  event for retained documents, an `SE_MOUSE` delta from the stock GUI's
  current cursor otherwise, both through the SDL3 backend's own window-to-GUI
  transform. A trigger pulled while the pointer rests on a menu becomes
  `K_MOUSE1` through the mouse-button path (never the usercmd poll queue) and
  stays a click until released. A 0.0015 dead band keeps hand tremor from
  re-hovering the menu every frame, which would also take focus from stick
  navigation. `idVRSystem::DrawMenuPointer`, called between
  `idSessionLocal::Draw` and `EndFrame`, draws a ringed dot over everything,
  since retained documents draw no cursor of their own.
- The retained pause and title screens cover the stock main menu, which stays
  the session's active GUI, and keep a cursor of their own. While VR has input
  focus the session holds the main menu's cursor on the covering screen's
  every frame, so the pointer's `SE_MOUSE` delta lands where the ray points.
- While the session is focused, losing desktop window focus neither releases
  VR input nor mutes audio. Menus ask `VR_HasInputFocus()` alongside the
  window: retained documents (`RetainedUI.cpp`) and retained screens in stock
  GUI slots (`idUserInterfaceRetained::AcceptInput`) otherwise suspend all
  input while the window, which a player in the headset cannot see, is
  unfocused. The first build missed both, and its smoke clicked a spot where
  a dead click looked the same as a live one; it now clicks Resume and
  requires the menu to close.

## Validation

- **Unit:** `tools/tests/native/VRMathCoreTest.cpp` covers axis conversion,
  orientation round trips, off-axis extents, snap/smooth turning, head-offset
  clamping and quad ray intersection.
- **Test runtime:** `tools/tests/openxr/OpenXRTestRuntime.cpp` is a minimal
  OpenXR 1.0 runtime with `XR_KHR_opengl_enable`, loaded through the normal
  loader with `XR_RUNTIME_JSON` (no system registration is touched). It
  simulates a stereo headset with off-axis eyes and two controllers, validates
  every submitted layer like a compositor (call order, released images, rects,
  poses, FOVs), plays a frame script of head/controller poses and button
  presses, and writes the submitted eye and quad images. It logs the first
  frames, every 90th, every capture and every change of layer layout, so a
  menu opening or closing is always on record; it also logs each haptic
  request with its hand. `burst <prefix> <frames> [scale]` writes the left eye
  of consecutive frames, shrunk, with each frame's mean luma in the log, for
  anything that comes and goes between frames, which one capture can miss.
- **Smoke:** `tools/tests/openxr_vr_smoke.py` runs the staged client against
  the test runtime on `game/airdefense1`: loading as a lone quad, then stereo
  gameplay with a scripted head turn and captures, the aim marker against a
  frozen world (`g_stopTime`: off, dot and beam captures differ only by the
  marker, a red dot in both eyes at one height whose disparity puts it on
  the hand's ray a few metres ahead; with `vr_leftHanded 1` the left
  controller's dot lands left of the right's), two-handed aim (the off hand squeezed on
  the foregrip raises the dot in both eyes, buzzes that hand and posts no
  weapon-wheel key), the comfort vignette (a smooth turn at full strength
  blacks out the top corners and leaves the centre clear), room scale (a
  0.5 m step leaves the
  head within 4 units of the origin; with `vr_roomScale 0` the same step
  stays a 19.7-unit lean), a physical crouch (a head 0.5 m down drops the
  body's eye by the crouch's 36 units, and rising restores it), the
  off-hand stick walking the body where the head faces and, with
  `vr_moveDirection 1`, where the off hand points (both from one spot and
  facing, in noclip, so terrain cannot bend them: 0 and 90 degrees off the
  facing), a snap
  turn, a trigger
  press reaching its binding, the controller's menu button opening the pause
  menu, and the pointer drawn where the scripted controller's ray meets the
  screen, on Resume, whose click must close the menu although the hidden test
  window never has focus, then a walker spawned and entered by script (its
  cockpit turns 45 degrees after a 45-degree head turn while the eye stays
  within a few units, in stereo). It checks the session lifecycle, that both eyes are lit
  and differ (parallax), that a head turn changes the image, that the HUD
  layer is a partial premultiplied overlay, and that the log is clean. Run it
  with `--basepath <Quake 4 install> --build-dir <build dir>` after staging
  `.install`.

  `tools/tests/openxr_vr_mp_smoke.py` hosts a listen server on `mp/q4dm1`
  and joins it in VR (the MP launch's `ui_autoJoin 0` is turned to 1): the
  match presents in stereo, a 0.5 m step walks the body after the head
  through the usercmd until the head is within 6 units, and with
  `vr_roomScale 0` the same step stays a 19.7-unit lean.

  The script's waits are in real time, and the development machine is
  shared: peers' builds and tests have dropped the stereo world to a few
  frames a second and stalled it for over a second, so a "laser off" capture
  caught a frame begun before the cvar changed, and `vr_status` reported the
  head before it moved. The SP smoke therefore lets frames run as well
  (`frame_guarded`: `wait 2` before each marker, `wait 3` after each
  real-time wait).

  The smokes skip cinematics (`g_autoSkipCinematics 1`). A probe that let
  airdefense1's intro play (2026-10-04) found every frame presenting the lone
  virtual screen with the cinematic on it, the starfield, Kane and the logo
  in turn, and a head turn during it moved nothing on the screen.

  The game's command buffer runs bindings behind whatever a script still has
  waiting (`waitMsec` keeps the rest of the buffer), so the smoke's trigger
  binding runs the second half of the script itself; a binding that `echo`es
  while a script waits would only print after the script's `quit`.

Measured on the smoke (debug build, 1200×1320 eyes, 90 Hz test runtime): the
paused game keeps rendering the world in stereo behind the menu, so menus
present a projection layer plus an opaque world-locked screen quad; gameplay
presents a projection layer plus the head-locked HUD quad with source-alpha
blending.
- **Hardware:** a real headset run is required before calling the feature done;
  it is listed as open in the release notes until someone reports it.

## Risks

- **No headset on the development machine.** Everything except the physical
  feel is checked against the test runtime; comfort and controller ergonomics
  need a player report.
- **Per-eye cost.** The front end runs twice per frame. Shadow maps that are
  view-independent are cached per frame; cascades are re-fitted per eye.
- **Runtime GL support.** SteamVR, the Oculus runtime and Monado support
  `XR_KHR_opengl_enable`; WMR does not (and is discontinued). A missing
  extension is reported and VR stays off.
- **Linux bindings.** The Xlib binding needs a GLX context, which SDL uses on
  X11 and XWayland. Native Wayland (EGL) needs `XR_MNDX_egl_enable` (phase 5).
  SDL's video subsystem starts before the configuration loads, so `vr_enable`
  cannot choose X11 itself; on Wayland desktops players start the game with
  the existing `OPENQ4_FORCE_X11=1`, which the warning and the user guide say.
- **View-weapon alignment.** Held weapons (see Game) measure each model's
  barrel and grip, so every stock gun sits in the hand along its laser. The
  grip estimate, halfway between wrist and index knuckle, is checked against
  the test runtime, where the grip and aim poses coincide; on a headset the
  grip pose is the palm, which needs a player's report.
- **Archived offsets from the first VR builds.** `vr_weaponOffset*` are
  archived, so every config written before held weapons keeps the old -5 and
  -3, which push each gun back and down out of the hand (off the bottom of
  the view for most of the stock guns). `Common_MigrateLegacyVRWeaponOffsets`
  resets exactly that pair to 0 once at startup
  (`vr_weaponOffsetDefaultMigrated`). The same stale pair in a reused test
  profile first looked like guns vanishing at random: test profiles keep
  archived cvars between runs, so a harness that needs a value must set it.
